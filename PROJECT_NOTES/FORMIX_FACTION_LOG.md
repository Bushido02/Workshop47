восстанавливать контекст заново, а сразу продолжать с точки остановки.

### 🔴 Активный незавершённый баг — ждёт лога от пользователя

**"FormixHive не даёт population supply, иногда 0/0"** — статически код
выглядит корректным (см. раздел 12.2 архива для полной цепочки разбора),
причина не найдена. Для диагностики в коде сейчас **активны два временных
диагностических лога**, которые нужно проверить/убрать в следующую
сессию:
- `building/BuildingClientEvents.java:101` — `[FORMIX-DEBUG-CLIENT-SUPPLY]`
  в `getTotalPopulationSupply()` (throttled, раз в секунду).
- `unit/UnitClientEvents.java:247` — `[FORMIX-DEBUG-CLIENT]` в
  `getCurrentPopulation()`, диагностирует второй, отдельный баг ("занятое
  население 0 vs 3 при разных выбранных юнитах").

**Следующий шаг:** запросить у пользователя `run/logs/latest.log` после
теста (построить Hive → выбрать юнита/здание), найти обе строки с
префиксами выше. **После получения лога и исправления обоих багов — ОБА
`System.out.println`/`sb.append` диагностических блока должны быть
удалены**, они не должны остаться в финальном коде.

**Урок, уже дважды подтверждённый в этом проекте:** методы с одинаковым
именем существуют раздельно в `Xxx**Server**Events` и `Xxx**Client**Events`
классах. Перед тем как класть диагностику в такой метод — `grep` по
вызывающему UI/HUD-коду, чтобы подтвердить, какая именно версия (Client
или Server) реально вызывается в конкретном отображаемом сценарии.

### Базовое состояние MVP-пайплайна Formix (с 19–21.07.2026, стабильно)
- Фракция Formix выбираема в лобби матча (F12/MatchStartScreen) и в
  debug-кнопках быстрого старта в углу экрана.
- `FormixWorkerUnit` — собирает ресурсы (включая item-дропы типа mutton/
  beef с убитых животных, `setCanPickUpLoot(true)` — это важно, была
  ошибка с `false`), строит/чинит здания, конвертируется в
  `FormixWarriorUnit` через ability "Call to Arms" у главного здания
  (требует `this.callToArmsGoal.tick()` вызова вручную в `tick()` юнита —
  это НЕ обычный goalSelector-goal, легко забыть при копировании паттерна).
- `FormixWarriorUnit` — боевой (melee), конвертируется обратно в worker
  через "Back to Work"; отвалится сам в worker'а, если уйдёт дальше 60
  блоков от Hive. Тоже `setCanPickUpLoot(true)`.
- `FormixHive` — главное здание, производит `FormixWorkerUnit`. Иконка —
  honeycomb block (временная, до своей постройки).
- Счётчик ресурсов (внутриигровые названия теперь "Рис"/"Эфир"/"Версиформ",
  см. раздел 12.1 архива — внутри кода/переменных по-прежнему food/wood/ore)
  — виден ТОЛЬКО на экране инвентаря (`InventoryScreen`/
  `CreativeModeInventoryScreen`), НЕ везде (это было изменено — раньше
  показывался поверх любого экрана, пользователь попросил сузить). Формат
  "текущее / 1000" — вертикальный список плашек в стиле unit_frame. Метод:
  `hud/HudClientEvents.onDrawScreenResourcesOverlay`.
- **Реальный лимит хранения ресурсов = 1000** на каждый тип (food/wood/ore).
  Это не только визуал — ресурсы физически перестают копиться после этой

  Creative — раньше был жёстко заблокирован. Потребовало раскомментировать

## 1. Статус на данный момент: MVP-пайплайн реализован, требует ручной проверки в Gradle

Сборка **не проверялась реальным компилятором** — в песочнице, где пишется

### 1.1 Баги, найденные и исправленные после первой реальной сборки (19.07.2026)

Пользователь прислал реальный вывод IntelliJ Gradle build. Исправлено:

1. **`FormixWarriorRenderer.java` содержал класс `FormixWorkerRenderer`**
   (неверное имя класса/конструктора внутри правильно названного файла).
   Причина: файл создавался через `sed` копированием `FormixWorkerRenderer.java`
   с заменой `FormixWorkerModel→FormixWarriorModel` и
   `FormixWorkerUnit→FormixWarriorUnit`, но САМО имя класса
   `FormixWorkerRenderer`/конструктор не входило ни под один из этих
   паттернов замены (замена была `s/FormixWorkerModel/FormixWarriorModel/g`
   и `s/FormixWorkerUnit/FormixWarriorUnit/g` — обе не матчат ровно
   `FormixWorkerRenderer`). Это вызвало каскад ошибок: duplicate class,
   "public class in wrong file", cannot find symbol FormixWarriorRenderer в
   ClientModEvents, type mismatch в registerEntityRenderer. **Урок:** при
   генерации файла через sed-копирование всегда явно заменять ПОЛНОЕ имя

После этих правок оставшиеся warnings в логе (`ResourceLocation(String,String)

### 1.2 Баг: фракция Formix не появлялась в экране выбора фракции (F12 лобби) — исправлено 19.07.2026

Пользователь сообщил, что в игре (экран выбора фракции перед стартом матча,
открывается клавишей, которую он назвал F12 — судя по коду это, скорее
всего, `MatchStartScreen`, отдельный полноценный UI-экран лобби, а не
`sandbox` режим, который был поправлен в первой итерации) фракция Formix не
отображалась среди плиток выбора, хотя Villagers/Monsters/Piglins были на
месте.

**Причина:** `matchstart/MatchStartScreen.java` содержит СОБСТВЕННЫЙ,
отдельный от `sandbox/SandboxClientEvents.java` жёстко закодированный
список фракций для отрисовки плиток выбора в лобби. Это отдельная точка
интеграции, которую я упустил при первичном аудите проекта — я нашёл и
поправил `PlayerServerEvents`/`PlayerServerboundPacket` (логика старта
матча) и `SandboxClientEvents` (песочница), но не увидел, что реальный,
основной UI выбора фракции для обычного RTS-матча рисуется в отдельном
классе `MatchStartScreen`.

**Что исправлено:**
1. `MatchStartScreen.java`: локальный массив `Faction[] order = {...}` внутри
   `renderSlotRow()` вынесен в поле класса `FACTION_TILE_ORDER` (добавлен
   `Faction.FORMIX`), используется в двух местах: цикл отрисовки плиток и
   расчёт ширины ряда фракций (`factionTotalW`), которые раньше жили
   раздельно и были рассинхронизированы (`FRAME_SIZE * 3` — магическое
   число под старые 3 фракции, не считая RANDOM). Теперь оба места
   вычисляются от `FACTION_TILE_ORDER.length`, что исключает повторение
   этого бага при добавлении новых фракций в будущем.
2. `startpos/StartPosClientEvents.java`: switch по `startPos.faction`,
   который задаёт превью здания-призрака при выборе стартовой позиции на
   карте, получил `case FORMIX -> Buildings.FORMIX_HIVE`. Без этого игрок,
   выбравший Formix, не видел бы превью здания при клике на карту (хотя
   само здание бы всё равно заспавнилось корректно при старте — это чисто
   UX-баг превью, не блокирующий).

**Урок на будущее:** при добавлении новой фракции нужно грепать
`switch.*faction`/`Faction\[\]`/`Faction\.VILLAGERS` по ВСЕМУ проекту, а не
только по тем файлам, что кажутся очевидными точками интеграции (player/
sandbox). Если добавляется что-то новое — сразу
`grep -rn "Faction.PIGLINS" src/` и проверять каждое совпадение, а не
полагаться на память о том, "где обычно бывают такие свитчи".

### 1.4 Баг: worker не конвертировался в warrior — исправлено 19.07.2026

**Причина:** `callToArmsGoal` создавался в `initialiseGoals()`, но никогда
не тикался. В отличие от большинства других goal-ов в этом проекте, которые
работают через стандартный Minecraft `goalSelector.addGoal(...)`,
`CallToArmsGoal`/`CallToArmsGoalFormix` — это goal особого рода: он
тикается **вручную** прямым вызовом `this.callToArmsGoal.tick()` внутри
`tick()` самого юнита (см. `VillagerUnit.tick()` строка ~384: `this.
callToArmsGoal.tick();` — стоит отдельной строкой рядом с `WorkerUnit.
tick(this)`, а НЕ добавлен в `goalSelector`). Я скопировал структуру
`initialiseGoals()`/`registerGoals()` из `VillagerUnit`, но упустил эту
единственную строку в `tick()`, поэтому объект goal существовал, но был
полностью мёртв — `isInRange()`/`convertToWarrior()` никогда не вызывались.

**Исправлено:** добавлена строка `this.callToArmsGoal.tick();` в
`FormixWorkerUnit.tick()`, сразу после `WorkerUnit.tick(this)` — 1:1 как в
оригинале.

**Урок на будущее:** goal-объекты в этом проекте бывают ДВУХ видов —
(1) обычные, добавленные через `goalSelector.addGoal(priority, goal)`
(тикаются автоматически движком Minecraft), и (2) "ручные" вспомогательные
goal-объекты вроде `CallToArmsGoal`, которые НЕ добавляются в
`goalSelector` и требуют явного `goal.tick()` внутри `tick()` юнита. При
копировании структуры юнита с полем типа `SomeGoal xxxGoal;` — всегда
проверять оба места: где создаётся (`initialiseGoals()`) И где тикается
(`registerGoals()` через addGoal ИЛИ `tick()` через прямой вызов), не
останавливаться после первого найденного места.

### 1.5 Баг: worker не подбирал дропы мяса (mutton/beef/etc.) с убитых животных — исправлено 19.07.2026

**Уточнение от пользователя:** речь шла именно про физические item-дропы,
падающие с убитых животных (mutton/beef/porkchop/etc.), не про блоки.

**Первая версия анализа (в этом файле) была неверной** — я решил, что эта
механика вообще не реализована в проекте. На самом деле она полностью
реализована и рабочая, я просто не проверил вызывающий код достаточно
глубоко в первый раз. Правильная картина:

- `resources/ResourceSources.getFromItem(Item)` резолвит предмет (BEEF,
  MUTTON, PORKCHOP, RABBIT, и т.д.) в `ResourceSource`/`ResourceName.FOOD`.
- `unit/UnitServerEvents.onDropItem(LivingDropsEvent)` — глобальный
  Forge-обработчик: когда `WorkerUnit` убивает "huntable" животное, дроп
  ОТМЕНЯЕТСЯ (`evt.setCanceled(true)`) и вместо ваниль-дропа юнит получает
  гарантированный набор еды напрямую (`ResourceSources.
  getFoodItemsFromAnimal(animal)` → `unit.getItems().add(...)`) — то есть
  killing an animal as a worker instantly banks food, no separate pickup
  step needed for that specific kill.
- Для дропов, которые всё-таки падают на землю (например животное убито НЕ
  worker'ом, или дроп от чего-то другого) — их подбирает
  `unit/interfaces/Unit.java` → `checkAndPickupResources(Unit)`, вызываемый
  каждый тик из `Unit.tick(unit)` (которое я уже вызываю в обоих
  Formix-юнитах). Этот метод сканирует `ItemEntity` в радиусе 1 блока и
  добавляет их в `unit.getItems()` через `ResourceSources.getFromItem(...)`.

**Реальная причина бага:** ОБА этих механизма (`onDropItem` мгновенный
дроп-в-руки И `checkAndPickupResources` подбор с земли) требуют
`((Mob) unit).canPickUpLoot() == true` как обязательное условие — это
первая же проверка в обоих местах. Я по ошибке поставил
`this.setCanPickUpLoot(false)` в обоих Formix-юнитах (`FormixWorkerUnit` и
`FormixWarriorUnit`), перепутав паттерн с чем-то другим. **Абсолютно все**
остальные юниты в проекте (проверено `grep`, 27 файлов) ставят `true` —
это универсальный паттерн, не зависящий от фракции.

**Исправлено:** `setCanPickUpLoot(false)` → `setCanPickUpLoot(true)` в
обоих файлах (`FormixWorkerUnit.java`, `FormixWarriorUnit.java`). Пустой
override `protected void pickUpItem(ItemEntity) {}` остаётся как есть (это
намеренно — блокирует ТОЛЬКО ваниль-логику визуального добавления предмета
в руку моба, не мешает подбору ресурсов, который идёт отдельным путём
через `checkAndPickupResources`/`onDropItem`).

**Важный нюанс:** мгновенный дроп-в-руки при убийстве (`onDropItem`)
требует `instanceof WorkerUnit` — `FormixWarriorUnit` этим интерфейсом
НЕ реализован (сознательно, см. раздел 5 — warrior не собирает ресурсы).
Значит warrior, убивший животное, НЕ получит мгновенный гарантированный
дроп еды тем же путём, что worker — животное просто даст обычный ваниль-
дроп на землю, который `checkAndPickupResources` подберёт (т.к. теперь
`canPickUpLoot() == true`), но без бонусов типа гарантированного количества
или `incrementHunterExp()`. Это соответствует поведению `MilitiaUnit`
(тоже не `WorkerUnit`) — то есть Formix ведёт себя симметрично villager-
паттерну, разницы в поведении между фракциями нет.

**Урок на будущее:** при копировании юнита из чужого паттерна — свериться
`grep -n "setCanPickUpLoot" оригинальный_файл.java` для КАЖДОГО значения
true/false, а не полагаться на память о том, "это наверное отключено у
воркеров чтобы не подбирали случайный мусор" (интуитивно кажется логичным,
но оказывается неверным — в этом проекте подбор всегда включен, просто
физическое добавление в РУКУ (визуал) отдельно заблокировано через
`pickUpItem()` override).

### 1.6 Фича: счётчик ресурсов (food/wood/ore), видимый поверх любого экрана — добавлено 19.07.2026

Пользователь хотел видеть свои ресурсы (дерево/еда/руда) в левом верхнем
углу при открытии обычного Minecraft-инвентаря, не переключаясь на
полноэкранный RTS-режим (в этом проекте называется "orthoview"/"topdown

"F12"; см. `keybinds/Keybindings.java` для точной привязки, по умолчанию
это `OrthoviewClientEvents`-переключатель).

**Важный нюанс архитектуры, обнаруженный по пути:** пока orthoview активен,
`player/PlayerClientEvents.onScreenOpen` СОЗНАТЕЛЬНО блокирует открытие
обычного Minecraft-инвентаря (`evt.setCanceled(true)` для
`InventoryScreen`/`CreativeModeInventoryScreen`) — то есть в самом RTS-виде
привычного инвентаря с сеткой предметов не существует. Значит запрос
пользователя относится к моменту, когда игрок НЕ в orthoview (обычная

обычный инвентарь клавишей E.

**Реализация:** новый метод `hud/HudClientEvents.
onDrawScreenResourcesOverlay(ScreenEvent.Render.Post)` — отдельный,
независимый от существующего `onDrawScreen` (который жёстко привязан к
`instanceof TopdownGui` и поэтому не годился для этой задачи напрямую).
Новый метод:
- Пропускает `TopdownGui` (там уже есть полная панель ресурсов через
  старый `onDrawScreen`, не дублируем).
- Показывается только пока `PlayerClientEvents.isRTSPlayer()` истинно
  (т.е. игрок реально участвует в активном RTS-матче) — не отвлекает людей
  вне матча / в ванильном одиночном Minecraft.
- Рисует 3 компактные иконки (food/wood/ore) с числами в левом верхнем
  углу (`startX=4, startY=4`), переиспользуя существующие рендер-хелперы
  `util/MyRenderer.renderFrameWithBg/renderIconFrameWithBg/renderIcon` и
  те же текстуры/цвета, что использует полная RTS-панель ресурсов
  (`textures/icons/items/wheat.png` и т.д.), чтобы визуально не выглядеть
  чужеродно.
- Это ПРОСТОЙ read-only виджет — без world-position подсчёта "сколько
  worker'ов назначено на этот ресурс" (в отличие от полной панели в
  `onDrawScreen`, там это есть) — не нужно для компактного индикатора, и
  такой подсчёт был бы избыточно дорогим для отрисовки на каждом кадре
  поверх произвольных экранов.

**Не является Formix-специфичной правкой** — это общая QoL-фича проекта,
работает для всех фракций одинаково (показывает ресурсы ТЕКУЩЕГО игрока,
не завязано на конкретную фракцию).

**Если нужно доработать:** позиция (`startX`/`startY`), порядок ресурсов
(`resourceOrder` массив), видимость (сейчас показывается на любом экране,
включая chat/pause — если нужно ограничить конкретными экранами, добавь
`evt.getScreen() instanceof XxxScreen` проверку в начале метода).

### 1.8 Ресурсы в инвентаре + RTS-режим в Survival/Adventure — 21.07.2026

**Часть A — счётчик ресурсов, переделан под референс пользователя.**
Пользователь прислал скриншот другого мода/пака: 3 вертикальные плашки
(иконка + число, широкая рамка с подсветкой), видимые ТОЛЬКО в инвентаре, а
не на весь экран как было раньше. Полностью переписан
`onDrawScreenResourcesOverlay` в `hud/HudClientEvents.java`:
- Условие видимости сужено с "любой экран" до строго
  `instanceof InventoryScreen || instanceof CreativeModeInventoryScreen`
  (оба импортированы явно).
- Layout сменён с горизонтального ряда мелких иконок на вертикальный
  список широких плашек (`rowWidth=150, rowHeight=34`, с отступом
  `rowSpacing=6` между строками), каждая через `MyRenderer.
  renderFrameWithBg(...)` — тот же готовый "unit_frame" стиль рамки,
  что используется для панелей юнитов в остальном HUD, для визуальной
  консистентности с общим стилем мода.
- Не показывает "/max" (в отличие от референс-скриншота), т.к. в этом
  моде у ресурсов нет фиксированного капа на 1000 — это архитектурное
  отличие оригинала, не то, что можно скопировать буквально.

**Часть B — RTS-режим (orthoview) разрешён в Survival и Adventure, не
только Creative.** Раньше `orthoview/OrthoviewClientEvents.java` жёстко
блокировал вход в RTS top-down вид в этих двух режимах (показывал ошибку
`hud.orthoview.reignofnether.ortho_error` и не давал включиться,
`tryToToggleEnable()`), и ДОПОЛНИТЕЛЬНО принудительно выключал orthoview
каждый тик, если игрок каким-то образом оказался в нём при Adventure/
Survival (в `onClientTick`-подобном методе). Оба ограничения убраны.

**Настоящая техническая причина ограничения (не просто "было лень
разрешить"):** включение orthoview телепортирует игрока на большую высоту
(`orthoviewPlayerBaseY = 100`) и держит его там для вида "сверху вниз".
В Creative это не проблема — creative-игроки летают по умолчанию. В
Survival/Adventure без специальной noclip/flight-логики игрок либо
проваливался бы в свободное падение сразу после телепорта, либо получал
fall damage при выходе из режима. Эта логика ФИЗИЧЕСКИ УЖЕ БЫЛА написана
автором мода — `mixin/PlayerMixin.java`, метод `tick()` — но была
полностью закомментирована и жёстко ограничена условием
`player.isCreative()`, с явным комментарием в коде: `"only needed if
orthoview players are in CREATIVE mode"`. Похоже автор либо тестировал
и что-то не заработало для non-Creative, либо просто не успел довести до
конца эту часть — история/git-лог для точного ответа недоступны.

**Что сделано:** раскомментирован `tick()` метод в `PlayerMixin.java`,
убрано условие `player.isCreative()` — теперь `noPhysics=true` и
`flying=true` принудительно ставятся для ЛЮБОГО игрока, находящегося в
orthoview (через `PlayerServerEvents.orthoviewPlayers` на сервере или
`OrthoviewClientEvents.isEnabled()` локально на клиенте), независимо от
геймтайпа. Класс `PlayerMixin` уже был зарегистрирован в
`reignofnether.mixins.json` (просто был no-op из-за закомментированного
тела) — не нужно ничего менять в конфигурации мода, только сам код.

**ВАЖНЫЙ РИСК, требующий проверки в реальной игре (я не могу это
протестировать без живого Minecraft-клиента):**
- Закомментированный оригинал имел комментарий: `"tick() naturally
  reverses all of this so no need for reversing it here when leaving
  orthoView"` — это предположение полагается на то, что ваниль-логика
  Minecraft сама сбрасывает `flying`/`noPhysics` при выходе из полёта. Это
  логично для Creative (там `flying` и так ожидаемое состояние), но
  **не гарантированно так же чисто работает для Survival/Adventure** —
  есть риск, что игрок останется "залипшим" в режиме полёта/без
  столкновений после выхода из orthoview в этих режимах, если ваниль не
  сбрасывает `getAbilities().flying` автоматически для них.
- **Если это произойдёт** (игрок продолжает летать/проваливается сквозь
  блоки после выхода из RTS-вида в Survival/Adventure) — быстрый фикс:
  в `OrthoviewClientEvents.toggleEnable()`, в ветке `else` (когда
  `enabled` становится `false`, т.е. выход из режима), явно добавить
  сброс `MC.player.getAbilities().flying = false;
  MC.player.onUpdateAbilities();` на клиенте, и аналогичный явный сброс
  `noPhysics`/`flying` на сервере в `PlayerServerEvents.
  disableOrthoview(int id)`. Не добавлено заранее, чтобы не чинить то,
  что возможно не сломано — сначала нужно реальное подтверждение бага в
  игре.
- Другой возможный риск: fall damage при телепортации ВНИЗ (например если
  сервер уменьшает `orthoviewPlayerBaseY` относительно текущей позиции
  игрока, или landscape под ним ниже базовой RTS-высоты) — раз
  `noPhysics=true` действует, пока `isEnabled()`/игрок в
  `orthoviewPlayers`, сам процесс нахождения в режиме должен быть
  безопасен, риск именно в моменте ВЫХОДА.
- Проверить также: голод/мобы-атаки в Survival, пока игрок находится в
  RTS-виде (сам orthoview не даёт неуязвимости, только noclip/flight —
  игрок физически стоит/висит в воздухе на `orthoviewPlayerBaseY`, куда
  агрессивные мобы не должны доставать, но это стоит перепроверить
  визуально).

**Если после тестов окажется, что риски выше некритичны** — эта фича
полностью рабочая end-to-end (сама блокировка входа снята, физика полёта
обеспечена для всех режимов). Если найдутся баги — присылай точное
описание (что произошло при выходе из orthoview в survival) и я поправлю
точечно, не откатывая всю фичу.

### 1.9 Лимит хранения ресурсов (1000) + уменьшение размера HUD-плашек — 21.07.2026

Пользователь прислал скриншот нового вида плашек ресурсов (после правки
1.8) — визуально они оказались слишком широкими (`rowWidth=150` для
короткого текста типа "500"). Плюс запрошен реальный (не только визуальный)
лимит хранения ресурсов по образцу скриншота "150/1000".

**Важный архитектурный факт, выясненный перед реализацией:** до этой
правки в моде НЕ было понятия лимита хранения ресурсов вообще — `Resources`
(в `resources/Resources.java`) хранил `food/wood/ore` как простые
неограниченные `int`. Это подтверждено пользователем явно как желаемое
геймплейное изменение (не просто текст в HUD), после уточняющего вопроса.

**Реализация — централизованный clamp внутри `Resources`, не в местах
вызова:**
- `MAX_RESOURCE_AMOUNT = 1000` — новая public static константа в
  `Resources.java`.
- `changeInstantly()` (server-side начисление) и `changeOverTime()`
  (client-side анимация счётчика) теперь клэмпят результат через приватные
  `clampTotals()`/`clampToAddFields()`. Только ДВА метода реально меняют
  ресурсы во всём проекте (`grep` подтвердил — 3 места вызова, все через
  эти два метода), поэтому клэмп в самом классе `Resources` защищает
  ВЕСЬ проект автоматически, без необходимости трогать вызывающий код
  (`ResourcesServerEvents`, `ResourcesClientEvents`, и любой будущий код).
- Траты (отрицательные изменения, покупка юнитов/зданий) НЕ блокируются
  клэмпом — `Math.min(x, MAX)` только режет положительный прирост сверху,
  никогда не мешает тратить то, что уже есть.
- `tick()` (постепенный "тающий" анимационный дренаж `foodToAdd` → `food`
  для HUD) не требует отдельного клэмпа — он не создаёт новое количество,
  только переносит уже клэмпнутое значение из `foodToAdd`, поэтому
  арифметически не может превысить лимит сам по себе.

**КРИТИЧЕСКИ ВАЖНОЕ ИСКЛЮЧЕНИЕ — sandbox-игроки:** обнаружено, что
sandbox-режим стартует игроков с `STARTING_FOOD_SANDBOX = 999999` (и
аналогично wood/ore) — специально безлимитные ресурсы для свободного
тестирования построек/юнитов без ограничений. Если бы clamp применялся
безусловно, ПЕРВАЯ ЖЕ трата в sandbox обрезала бы `999999` до `1000`
(т.к. `changeInstantly(-цена)` вызвал бы `clampTotals()`, а
`Math.min(999999 - цена, 1000) = 1000`), сломав весь смысл sandbox-режима.
Поэтому оба clamp-метода начинаются с проверки
`SandboxServer.isSandboxPlayer(this.ownerName)` — если true, клэмп
полностью пропускается, sandbox остаётся безлимитным как и было.
(Небольшая архитектурная деталь: `isSandboxPlayer` читает server-side
список `PlayerServerEvents.rtsPlayers`, значит на выделенном/dedicated
сервере вызов этого метода из клиентского `changeOverTime()` может не
видеть актуальный список — на practice это не критично, т.к. авторитетное
значение всё равно придёт с сервера следующим тиком, но если когда-то
понадобится 100% чистое разделение client/server логики здесь — стоит
передавать флаг "является ли sandbox" явным параметром вместо обращения к
серверному синглтону изнутри модели данных.)

### 1.10 Population: Warrior не считался в занятом населении (исправлено) + Hive supply=0 (диагностика начата, НЕ завершена) — 25.07.2026

**Часть A — исправлено.** Пользователь сообщил: при конверсии worker→warrior
юнит "пропадал" из занятого населения (счётчик X/Y уменьшался), при
обратной конверсии в worker снова появлялся. Причина найдена сразу:
`ReignOfNetherCommonConfigs.UnitCosts.FORMIX_WARRIOR` был объявлен с
`population=0` (`ResourceCostConfigEntry.Unit(food, wood, ore, seconds,
population, ...)`), тогда как `FORMIX_WORKER` имел `population=1`.
`UnitServerEvents.getCurrentPopulation()` суммирует `unit.getCost().
population` по всем живым юнитам заново при каждом подсчёте — конверсия
никак не трогает population вручную, значение просто берётся из текущего
конфига юнита. Исправлено: `FORMIX_WARRIOR` теперь `population=1`.

**Часть B — НЕ завершено, начата диагностика.** Отдельная жалоба:
`FormixHive` после постройки не даёт population supply, счётчик всегда
0/0 (при том что `BuildingCosts.FORMIX_HIVE` в конфиге содержит
`supply=5`, ещё с сессии от 23.07 — раздел ниже "23.07.2026 (сессия про
баланс population)"). Прошёл ВСЮ цепочку статически, не нашёл разницы с
рабочим `TownCentre`:
1. `ReignOfNetherCommonConfigs.BuildingCosts.FORMIX_HIVE` — `supply=5`,
   4-й параметр `Building(food, wood, ore, supply, ...)`, синтаксически
   верно.
2. `ResourceCosts.FORMIX_HIVE.bakeValues(ReignOfNetherCommonConfigs.
   BuildingCosts.FORMIX_HIVE)` — вызывается в `ResourceCosts.
   deferredLoadResourceCosts()`, которая в свою очередь вызывается и на
   сервере (`ReignOfNether.java`), и на клиенте (`ConfigClientEvents.java`)
   — идентично другим зданиям, не Formix-специфично.
3. `ResourceCost.bakeValues()` читает `rcce.getPopulation()` →
   `this.POPULATION.get()` (ForgeConfigSpec-значение) — стандартный,
   работающий у всех зданий путь.
4. `FormixHive.cost = ResourceCosts.FORMIX_HIVE` — `public final static`
   поле, тот же паттерн, что `TownCentre.cost = ResourceCosts.
   TOWN_CENTRE` (проверено построчным сравнением обоих файлов).
5. `Building(String structureName, ResourceCost cost, boolean isCapitol)`
   конструктор — просто `this.cost = cost;` (присваивание ссылки, не
   копия) — значит поздний `bakeValues()` обязан быть виден через
   `FormixHive.cost.population` тоже, т.к. это тот же объект в памяти.
6. `FormixHive()` конструктор — `super(structureName, cost, true)`,
   `isCapitol=true` передан верно (важно, т.к. `isCapitol` используется в
   других местах — граница застройки и т.д., раздел "22.07.2026,
   продолжение" — но не влияет на `getTotalPopulationSupply()` напрямую,
   проверено, что этот метод его не читает).
7. `Buildings.FORMIX_HIVE = register(..., new FormixHive())` — стандартная
   регистрация, идентична другим зданиям.
8. `BuildingServerEvents.getTotalPopulationSupply(ownerName)` — цикл по
   `buildings`, условие `building.ownerName.equals(ownerName) &&
   building.isBuilt`, суммирует `building.getBuilding().cost.population`
   — НЕТ никакой фильтрации по типу/классу здания, работает одинаково для
   любого `BuildingPlacement`.
9. `BuildingPlacement.isBuilt = true` выставляется в общем, не
   Formix-специфичном коде (сработавший `discardStructureVoidBlocks()`/
   завершение стройки) — не должно зависеть от того, что `FormixHive`
   временно использует чужую NBT-структуру `town_centre` (сам механизм
   постройки/структур не завязан на семантику "что это за здание", только
   на геометрию блоков).

**Ни на одном из этих 9 шагов не найдено расхождения с рабочим
`TownCentre`.** Вывод: причина либо в чём-то, не видимом статическим
анализом (реальный порядок событий Forge при загрузке, специфика
конкретной игровой сессии пользователя), либо в файле/месте, которое ещё
не проверено (например `ResourceCostsClientboundPacket`/сетевая
синхронизация supply на клиент — не проверялось в этой сессии, стоит
посмотреть в следующей, если лог не даст ответа сразу).

**Временный диагностический код добавлен** — `System.out.println` внутри
`BuildingServerEvents.getTotalPopulationSupply()`, помечен комментарием
`TEMP DEBUG (Formix population supply investigation, remove after

### 1.12 Найдена причина, почему серверный диагностический лог для Hive supply никогда не срабатывал — 25.07.2026, поздний вечер

Пользователь прислал полный `run/logs/latest.log` после теста (построил
`FormixHive`, дождался полной постройки, кликнул по зданию/юниту в
пределах времени лога) — в логе НЕТ НИ ОДНОЙ строки `[FORMIX-DEBUG]`
(лог из раздела 1.10), при этом подтверждено: здание построено, клик по
юниту/зданию точно был сделан вовремя.

**Настоящая причина — архитектурная, не связана с самим population-багом
напрямую.** В проекте есть ДВЕ ОТДЕЛЬНЫЕ реализации
`getTotalPopulationSupply()` с одинаковым именем в разных классах:
- `BuildingServerEvents.getTotalPopulationSupply(String ownerName)` —
  серверная, использует серверный список `buildings`. Используется в
  `ProductionItem`/при проверках возможности постройки на сервере — НЕ
  в отрисовке HUD.
- `BuildingClientEvents.getTotalPopulationSupply(String playerName)` —
  ОТДЕЛЬНАЯ клиентская, свой список `buildings` (синхронизированный по
  сети). **Именно эта версия вызывается из `HudClientEvents.java`
  (строка ~1164), то есть именно её результат видит игрок в панели
  ресурсов.**

Диагностический лог из раздела 1.10 был по ошибке добавлен в СЕРВЕРНУЮ
версию — решение основывалось на совпадении имени метода и идентичной
логике, без явной проверки (`grep`), какой конкретно класс вызывается
из `HudClientEvents`. Отсюда полное отсутствие лога — метод, который
логировался, физически не вызывался в контексте отрисовки HUD.

**Исправлено:**
- Убран бесполезный лог из `BuildingServerEvents.
  getTotalPopulationSupply()`, метод возвращён к чистому оригинальному
  виду.
- Добавлен НОВЫЙ throttled лог (раз в секунду) в `BuildingClientEvents.
  getTotalPopulationSupply()` — правильное место. Префикс
  `[FORMIX-DEBUG-CLIENT-SUPPLY]` (намеренно отличается от старого
  `[FORMIX-DEBUG]`, чтобы не создавать путаницы, если пользователь по
  привычке будет искать старый префикс). Выводит `playerName`, `result`,
  полный список известных клиенту зданий с `owner`/`isBuilt`/
  `costPopulation`.

**Оба диагностических лога сейчас активны и оба в правильных местах:**
1. `[FORMIX-DEBUG-CLIENT-SUPPLY]` (`BuildingClientEvents.
   getTotalPopulationSupply`) — про Hive supply=0.
2. `[FORMIX-DEBUG-CLIENT]` (`UnitClientEvents.getCurrentPopulation`) —
   про занятое население, разное при разных выбранных юнитах (раздел
   1.11).

**Также уточнено, как пользователю искать лог надёжно:** панель Run в
IntelliJ иногда не открывает встроенный поиск по `Ctrl+F` корректно —
надёжнее открыть файл `run/logs/latest.log` напрямую (он в дереве
проекта) и искать текст там любым текстовым редактором/поиском файла.

**Следующий шаг:** получить от пользователя `run/logs/latest.log` (или
текст с обоими префиксами) после НОВОГО теста с этой версией кода. После
получения — исправить оба бага и обязательно убрать оба лога.

**Урок на будущее (важно для этого проекта конкретно):** в этом Forge-
моде одноимённые методы часто существуют раздельно в `XxxServerEvents` и
`XxxClientEvents` классах (стандартный паттерн клиент-серверного разделения
состояния) — при добавлении диагностики в такой метод ОБЯЗАТЕЛЬНО сначала
`grep` по вызывающему UI/HUD-коду, чтобы подтвердить, какая именно версия
(Client или Server) реально задействована в конкретном отображаемом
сценарии, прежде чем логировать не тот метод и тратить целый цикл
тестирования впустую.

## 2. Концепция фракции

- Фракция называется **Formix**.
- Основа — **полностью кастомные мобы** (не ре-текстур ваниль-моба), модели
  делаются в Blockbench пользователем.
- **Worker/Warrior механика** как у Villagers/Militia:
    - `FormixWorkerUnit` — рабочий: собирает ресурсы, строит/чинит здания.
    - `FormixWarriorUnit` — боевая форма, получается конверсией из worker'а
      у главного здания (`FormixHive`), возврат обратно возможен через
      ability "Back to Work".
- Один тип production-здания на этом этапе: `FormixHive` (аналог TownCentre),
  производит только `FormixWorkerUnit`. Warrior производится ТОЛЬКО через
  конверсию, отдельного Prod-класса для него нет и не нужно.

## 5. Архитектурные решения, которые стоит помнить

- **UnitAction переиспользование**: Formix-абилки используют те же
  `UnitAction.CALL_TO_ARMS_UNIT/BUILDING`, `BACK_TO_WORK_UNIT/BUILDING`
  enum-константы, что и Villagers. Это безопасно, т.к. `UnitAction` в этом
  проекте — просто ID для кнопки/сетевого пакета, диспетчеризация происходит
  через сам объект `Ability`, прикреплённый к конкретному юниту/зданию
  (`this.abilities.add(...)`), а не через центральный switch по `UnitAction`.
  Если это когда-то изменится (кто-то добавит централизованный switch по
  UnitAction) — тогда потребуется развести на отдельные значения.
- **I18n-ключи РАЗВЕДЕНЫ**: в отличие от UnitAction, для текста в `en_us.json`
  Formix-абилки используют СВОИ ключи (с суффиксом `_formix`), а не общие
  `abilities.reignofnether.call_to_arms_unit` и т.д. Причина: те ключи
  жёстко содержат текст про "Militia"/"Town Centre", который был бы неверен
  для Formix.
- **FormixWarriorUnit не implements WorkerUnit** — сознательно, т.к. warrior
  не занимается сбором ресурсов/стройкой, только боем. Хранит
  `resourcesSaveData` (тип `TargetResourcesSave`) чтобы восстановить
  worker'у его прежнее назначение при обратной конверсии.
- **Базовый класс — `Monster`, не наследование ваниль-моба.** В отличие от
  Piglins-юнитов (`GruntUnit extends Piglin` и т.п.), Formix-юниты следуют
  паттерну `WraithUnit extends Monster` — т.к. используют полностью
  кастомную (не ваниль) модель. Это правильный путь для кастомных мобов.
- **WARRIOR_RANGE = 60** (константа в `FormixHive`) — дистанция, на которой
  warrior остаётся конвертированным, аналог `TownCentre.MILITIA_RANGE`.
  Можно потом вынести в конфиг, если понадобится балансировка.
- **Стоимости (config defaults)**:
    - `FormixWorker`: 50 food, 15 сек, 1 pop (= Grunt/Villager baseline)
    - `FormixWarrior`: 0 food/food-cost, но "стоит" 20 wood (символическая
      стоимость конверсии, т.к. Prod-класса нет — это просто дефолтное
      значение конфига, реально не расходуется при конверсии сейчас).
      **Пересмотри это значение**, возможно стоит сделать конверсию
      полностью бесплатной (0 во всех полях) либо явно списывать ресурсы в
      `convertToWarrior()`, если хочешь баланс "конверсия стоит ресурсов".
    - `FormixHive`: 400 wood, 0 ore (= похоже на TownCentre, но без ore-cost
      — подправь под баланс своей игры).

## 10. Про Claude Project и GitHub-коннектор — 21.07.2026

Пользователь показал скриншот настроек Claude (Settings → Connectors), где
"GitHub Integration" помечен как **connected** на уровне аккаунта. Важное
уточнение, зафиксированное в этой сессии: подключение коннектора к
аккаунту НЕ означает автоматическую доступность в каждом чате — коннекторы
могут быть включены точечно per-чат/per-проект. В сессии, где велось это
обсуждение, GitHub-инструмент физически не подгрузился при `tool_search`
(только Notion-инструменты были доступны), несмотря на видимый статус
"connected" в общих настройках. Вероятная причина: коннектор активен для
ДРУГОГО чата/проекта пользователя ("Переработка GitHub проекта" был виден
в списке недавних чатов на скриншоте), не для этого разговора.

**Что это значит для будущих сессий этого проекта:** если пользователь
создаст Claude Project для этого мода и подключит туда GitHub — **не
предполагай автоматически, что GitHub-инструмент доступен**, даже если
пользователь упоминал, что "включил" его где-то. В начале сессии, где
GitHub может быть релевантен (например пользователь просит прочитать
файл из репозитория напрямую) — сначала попробовать `tool_search` с
релевантными терминами ("github", "repository", "pull request" и т.п.), и
если ничего не найдётся — прямо сказать пользователю, что инструмент не
подгрузился в этом чате, и спросить, включён ли он именно для этого
чата/проекта, а не просто "подключён к аккаунту".

**Даже если GitHub-инструмент когда-то станет доступен** — это даёт
возможность ЧИТАТЬ репозиторий (и, возможно, некоторые операции записи,
в зависимости от того, какие именно tools предоставляет конкретный
коннектор — не предполагай возможности заранее, проверяй фактический
список инструментов после `tool_search`). Это НЕ то же самое, что
произвольный `git clone`/`push` через bash — тот механизм технически
пробовался в этой же сессии и **сработал для публичного репозитория**
(`git clone`/`git ls-remote` через bash реально отработали для
`github.com/octocat/Hello-World`), но: (а) это не гарантированная,
документированная возможность — network allowlist может отличаться в
других сессиях, (б) для ЧАСТНОГО репозитория пользователя потребуется
аутентификация (токен), которой у ассистента нет и не должно быть
(хранение секретов между сессиями не предусмотрено), поэтому это не
практичный путь для реальной работы с приватным репо пользователя.
Единственный надёжный канал остаётся: пользователь загружает файлы в чат
→ ассистент правит → отдаёт файлы обратно. GitHub (через Project
Knowledge или коннектор, если станет доступен) — это удобство поверх
этого процесса, не замена ему.

— неочевидный механизм, специально проверен отдельно, подтверждено что
покрывается той же заменой файлов.
