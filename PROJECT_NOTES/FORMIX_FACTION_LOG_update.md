## 14. Замена placeholder-модели Warrior на реальную Blockbench-модель — 04.08.2026

Пользователь прислал `.bbmodel` (Blockbench source, не Java-экспорт) —
"Ополченец_1 - Converted.bbmodel" — и текстуру `formix_warrior_unit.png`
(64×64, старый placeholder-файл, не финальная текстура под новую модель).

### 14.1 Формат входного файла и решения по нему

`.bbmodel` — это JSON-исходник Blockbench (box_uv, 42 куба, 27 костей),
не "Export Java Entity" (которого раздел 4.1 инструкций проекта ожидает
как стандартный workflow). Пришлось писать конвертер `.bbmodel → Java`
вручную (Python-скрипт, координаты и иерархия костей извлечены из полей
`elements`/`groups`/`outliner` файла), т.к. готового Java-класса не было.

**Разобранные находки при анализе файла:**
- Разрешение текстуры в модели — 128×128, у присланного PNG — 64×64.
  Пользователь подтвердил: растянуть 64×64 до 128×128 (nearest-neighbor,
  без сглаживания) как временное решение.
- Анимации в файле (`idle`, `walk`, `бег`, `angry`) оказались нерабочими:
  `idle`/`walk` — все каналы с 0 keyframes (пустые), `бег` — keyframes
  есть, но привязаны к именам костей другого рига (`bone`, `LeftArm`,
  `RUpperLeg` и т.п.), не совпадающим с именами костей в этой модели
  (`ЛеваяРука`, `ПраваяНога`...). Пользователь подтвердил: вставить только
  статичную геометрию, анимации сделать простыми процедурными в коде.
- Оружие ("Бита"/bat) в иерархии подвешено к `leftArmLower`
  (то есть на "ЛеваяРука"), не на "ПраваяРука" — важно для анимации атаки.

### 14.2 Как проверялась геометрия перед отправкой (без живого Minecraft)

Т.к. `context.bakeLayer()` невозможно вызвать без Forge classpath, для
проверки правильности сборки использованы два независимых метода:
1. Визуальный — 3D-рендер всех 42 кубов напрямую из исходных абсолютных
   координат `.bbmodel` через matplotlib (Python), чтобы визуально
   подтвердить, что геометрия в принципе образует узнаваемую гуманоидную
   фигуру (голова/торс/руки/ноги на своих местах) до какой-либо
   Java-генерации.
2. Математический — реконструкция world-координат каждого куба и origin
   каждой кости из сгенерированных relative-координат (то, что попадёт
   в `addBox()`/`PartPose.offset()`) и сравнение с исходными абсолютными
   значениями из `.bbmodel`. Оба прогона (42 куба, 27 костей) совпали без
   расхождений до генерации итогового `.java`.

**Этот метод проверки не поймал баг, описанный в 14.3** — он проверяет
только относительные координаты внутри моей же сгенерированной структуры,
а не то, как эта структура соотносится с фактическим API Minecraft
(`context.bakeLayer()`). Разница между "геометрия внутренне непротиворечива"
и "геометрия корректно интегрируется с рантаймом Minecraft" — раздельные
проверки, полезно помнить в следующий раз при похожей задаче.

### 14.3 Баг после первого запуска: `NoSuchElementException: Can't find part bodyRotation`

Пользователь собрал и запустил (`runClient`), игра упала при первом
рендере юнита-warrior:
```
java.lang.IllegalArgumentException: Failed to create model for reignofnether:formix_warrior_unit
Caused by: java.util.NoSuchElementException: Can't find part bodyRotation
```

**Причина:** в исходном `.bbmodel` верхняя Blockbench-группа называется
"Формикс", и её единственный child — "Teло" (это и есть кость, которую я
переименовал в `bodyRotation`). Я 1:1 воспроизвёл эту структуру в
`createBodyLayer()`: создал промежуточный `PartDefinition root` (=
"Формикс") как child синтетического `partdefinition`, а `bodyRotation`
как child этого `root`. Но `context.bakeLayer(LAYER_LOCATION)` в
конструкторе `FormixWarriorModel(ModelPart root)` возвращает не
Blockbench-группу "Формикс", а **сам синтетический корень**
`meshdefinition.getRoot()` — то есть тот же уровень, что и мой
промежуточный `"root"` PartDefinition, а не его родитель. Значит вызов
`root.getChild("bodyRotation")` в конструкторе искал `bodyRotation` среди
детей несуществующего на этом уровне узла — на самом деле `bodyRotation`
был на один уровень глубже (child моего лишнего `"root"` бона, которого
конструктор вообще не запрашивал).

**Исправлено:** промежуточный Blockbench-бон "Формикс" убран из
`createBodyLayer()` — `bodyRotation` теперь добавляется напрямую как
`partdefinition.addOrReplaceChild("bodyRotation", ...)`, с суммарным
offset `(0, 16, 0)` (было: root=+16Y, bodyRotation=+0Y относительно root;
стало: bodyRotation=+16Y напрямую — то же итоговое мировое смещение).
Конструктор `root.getChild("bodyRotation")` теперь находит кость на
правильной глубине.

**Урок на будущее (важно для любой следующей Blockbench→Java конвертации
в этом проекте):** `context.bakeLayer(LAYER_LOCATION)` всегда отдаёт
СИНТЕТИЧЕСКИЙ корень Minecraft (`meshdefinition.getRoot()`), а не
верхнеуровневую группу из `.bbmodel`. Если у экспортируемой/конвертируемой
модели в Blockbench есть единственная root-группа, оборачивающая весь
риг (как здесь — "Формикс" вокруг "Teло") — эту обёртку нужно **схлопнуть
при генерации**: первый содержательный бон должен цепляться прямо к
`partdefinition`, не к промежуточному узлу-обёртке. Настоящий Blockbench
"Export Java Entity" делает это автоматически (see `WraithModel.java` —
там `bodyrotation` тоже добавлен напрямую к `partdefinition`, без обёртки) —
при ручной конвертации `.bbmodel` (не через официальный экспорт) это
нужно учитывать явно, как отдельный шаг, а не просто транслировать
Blockbench-иерархию 1:1.
