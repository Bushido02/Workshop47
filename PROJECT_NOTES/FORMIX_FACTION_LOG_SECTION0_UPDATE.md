## 0. АКТУАЛЬНОЕ СОСТОЯНИЕ (читать в первую очередь)

**Последнее обновление:** 28.07.2026 — оба population-бага найдены и исправлены.

### ✅ Population supply у FormixHive = 0 — ПРИЧИНА НАЙДЕНА И ИСПРАВЛЕНА

**Настоящая причина не имела отношения к коду.** Весь код (getTotalPopulationSupply,
bakeValues, ResourceCostConfigEntry и т.д.) был и остаётся корректным — статический
анализ в предыдущих сессиях был прав, расхождений с TownCentre не было.

**Реальная причина:** устаревший `.toml`-конфиг файл на диске (`run/config/
reignofnether-common.toml` или аналог), в котором для `FORMIX_HIVE` было сохранено
`Population value = 0` — это значение записалось туда в одной из первых тестовых
сессий (до того как дефолт `population=5` был выставлен в
`ReignOfNetherCommonConfigs.BuildingCosts.FORMIX_HIVE` в коде). Forge не перезаписывает
уже существующие ключи конфига при смене дефолта в коде — новый дефолт применяется
только если ключа ещё нет в файле. Пользователь вручную поправил значение в .toml
(или удалил файл), после чего в игровом чате подтвердилось: `cost.population=5`,
`supply=5` — всё корректно.

**Диагностика, которая довела до причины:** обычные логи (`run/logs/latest.log`)
оказались ненадёжным каналом в этой ситуации — несколько раз подряд пользователь
присылал логи от "неправильных" игровых сессий (где здание не успевало
достроиться, или тестирование конверсии происходило в другом запуске, чем тот, чей
`latest.log` был прислан). Решение — вывод диагностики **прямо в игровой чат**
(`ServerPlayer.sendSystemMessage`), а не в файл лога: сообщение появляется
немедленно на экране в момент события (постройка здания завершена / нажата Call to
Arms), исключая путаницу с тем, какой файл/сессия релевантны. **Урок на будущее:**
если пользователь испытывает сложности с тем, чтобы прислать релевантный
`latest.log` (несколько сессий подряд лог не содержит ожидаемых событий) — сразу
переключаться на чат-сообщения вместо `System.out.println`, не тратить лишний цикл
на очередной запрос лога.

**Диагностический код удалён** из `BuildingPlacement.onBuilt()`,
`BuildingClientEvents.getTotalPopulationSupply()`, `UnitClientEvents.
getCurrentPopulation()` — все три чисто вернулись к оригинальному виду.

### ✅ Мерцание населения при конверсии worker↔warrior (3→6→3) — ИСПРАВЛЕНО

**Причина:** `ConvertableUnit.convertToUnit()` (общий метод для всех фракций,
не только Formix) создавал новую сущность (`level.addFreshEntity(newEntity)`)
немедленно на сервере, но старая сущность (`oldEntity`) НЕ удалялась сразу —
удаление откладывалось до отдельного клиент-серверного round-trip через кастомный
пакет `UnitAction.DISCARD` (`UnitConvertClientboundPacket.syncConvertedUnits` →
клиент помечает `shouldDiscard=true` → следующий `tick()` юнита вызывает
`this.discard()`). Это создавало окно в несколько тиков, где на сервере
одновременно существовали и старый, и новый юнит — population считался по обоим,
отсюда временный скачок.

**Исправлено:** `oldEntity.discard()` теперь вызывается **немедленно** внутри
`convertToUnit()`, сразу на сервере, вместо отложенного пути через кастомный пакет.
Ваниль `discard()` сам корректно синхронизирует удаление всем клиентам через
стандартный entity tracker (`ClientboundRemoveEntitiesPacket`) — кастomный
`DISCARD`-пакет, который клиент всё равно шлёт следом (внутри `syncConvertedUnits`,
для сохранения выделения/групп/целей), просто становится no-op на уже
несуществующем ID юнита (`level.getEntity(id)` вернёт null, юнит безопасно
пропускается в цикле `UnitActionItem`). Это универсальный фикс — применяется не
только к Formix, но и к Villagers (VillagerUnit↔MilitiaUnit), т.к. затрагивает
общий интерфейс `ConvertableUnit`, не Formix-специфичный код.

**Затронутый файл:** `unit/interfaces/ConvertableUnit.java`, метод
`convertToUnit()`.

**Не проверено вживую после этого конкретного фикса** (правка сделана в конце
сессии) — при следующем тесте обрати внимание, не появилось ли новых проблем с
выделением юнита/group control сразу в момент конверсии (это то, ради чего
изначально был отложенный путь, судя по комментарию в оригинальном коде — "so the
client has a chance to sync goals, command groups and selections"). Если что-то
сломается в этой области — смотри сюда в первую очередь.
