### ✅ ЗАКРЫТО: Population supply у FormixHive = 0

**Причина не имела отношения к Java-коду.** Весь код (`getTotalPopulationSupply`,
`bakeValues()`, `ResourceCostConfigEntry` и т.д.) был и остаётся корректным —
множественные статические разборы в сессиях 25–27.07 не находили расхождений
с рабочим `TownCentre`, и они были правы.

**Реальная причина:** устаревший `.toml`-конфиг на диске (`run/config/
reignofnether-common.toml`), где для `FORMIX_HIVE` было физически сохранено
`Population value = 0` — записалось туда в одной из первых тестовых сессий,
до того как дефолт `population=5` был выставлен в
`ReignOfNetherCommonConfigs.BuildingCosts.FORMIX_HIVE` в коде. **Forge не
перезаписывает уже существующие ключи `.toml` при смене дефолта в коде** —
новый дефолт из кода применяется только если ключа ещё нет в файле вообще.
Пользователь вручную поправил значение в `.toml` (или удалил файл, дав Forge
пересоздать его) — после этого в игре подтвердилось: `cost.population=5`,
`supply=5`, всё корректно.

**Урок на будущее, важный конкретно для этого проекта:** если после смены
дефолтного значения в `ReignOfNetherCommonConfigs` баланс/поведение не
меняется в игре — **первым делом проверить существующий `.toml` в
`run/config/`**, а не искать баг в Java-коде. Конфиги Forge читаются один раз
при первом создании файла; повторные правки дефолтов в коде игнорируются,
пока файл уже существует на диске.

**Диагностический метод, который довёл до причины:** обычные файлы
`run/logs/latest.log` оказались ненадёжным каналом в этой конкретной
ситуации — несколько сессий подряд пользователь присылал логи от
"нерелевантных" запусков (здание не успевало достроиться до выхода из игры,
или тест конверсии происходил в другом запуске, чем тот, чей log был
прислан). Решение — вывод диагностики **прямо в игровой чат**
(`ServerPlayer.sendSystemMessage(Component.literal(...))`), а не в
`System.out.println`/файл: сообщение появляется сразу на экране в момент
события. **Если в будущем повторится ситуация "лог не показывает ожидаемых
строк несколько раз подряд" — сразу переключаться на игровой чат, не
запрашивать очередной лог.**

Весь временный диагностический код (в `BuildingPlacement.onBuilt()`,
`BuildingClientEvents.getTotalPopulationSupply()`,
`UnitClientEvents.getCurrentPopulation()`,
`ability/abilities/formix/CallToArmsUnitFormix.java`,
`ability/abilities/formix/CallToArmsBuildingFormix.java`) — **удалён**, все
файлы возвращены к чистому виду без чат-сообщений/println.

### ✅ ЗАКРЫТО: Мерцание занятого населения при конверсии (3→6→3)

**Причина:** `unit/interfaces/ConvertableUnit.convertToUnit()` — общий метод
для ВСЕХ конвертируемых юнитов проекта, не только Formix (затрагивает и
Villagers: VillagerUnit↔MilitiaUnit). Новая сущность создавалась на сервере
немедленно (`level.addFreshEntity(newEntity)`), а старая — НЕ сразу: удаление
было отложено до отдельного клиент-серверного round-trip через кастомный
пакет (`UnitConvertClientboundPacket.syncConvertedUnits` → клиент помечает
`shouldDiscard=true` → следующий `tick()` юнита вызывает `this.discard()`).
Это создавало окно в несколько тиков, где на сервере одновременно
существовали и старый, и новый юнит одновременно — population считался по
обоим, отсюда видимый скачок.

**Исправлено:** `oldEntity.discard()` теперь вызывается немедленно внутри
`convertToUnit()`, сразу на сервере — убрано ожидание отложенного пакета.
Ваниль `discard()` сам корректно синхронизирует удаление всем клиентам через
стандартный entity tracker; кастомный `DISCARD`-пакет, который клиент всё
равно шлёт следом (для сохранения выделения/групп/целей юнита), становится
безопасным no-op на уже не существующем ID (`level.getEntity(id)` возвращает
`null`, юнит просто пропускается в цикле `UnitActionItem`, ошибки нет).

**Побочная ошибка компиляции при первой попытке фикса и как она была
исправлена:** изначально код был написан как
`if (this instanceof ConvertableUnit convertable) convertable.setShouldDiscard(true);`
— это не скомпилировалось с ошибкой `expression type ConvertableUnit is a
subtype of pattern type ConvertableUnit`, потому что метод целиком объявлен
**внутри самого интерфейса `ConvertableUnit`** — `this` там уже статически
гарантированно имеет тип `ConvertableUnit`, компилятор Java не разрешает
`instanceof`-проверку типа на то, что и так этим типом является. Исправлено
на прямой вызов `this.setShouldDiscard(true);` без каста/проверки.

**Затронутый файл:** `unit/interfaces/ConvertableUnit.java`, метод
`convertToUnit()`. Правка общая для проекта (не только Formix) — теоретически
может повлиять и на конверсию Villagers, но по описанию логики должна быть
только исправлением, не регрессией.

**НЕ до конца проверено вживую (следующая сессия должна перепроверить):**
оригинальный (закомментированный) код имел пометку "so the client has a
chance to sync goals, command groups and selections" — то есть отложенный
discard был сделан НАМЕРЕННО автором мода, предположительно чтобы клиент
успевал прочитать состояние старой сущности (текущие цели/группа
управления/выделение) до её удаления. Немедленный `discard()` теоретически
безопасен (это разные стороны: discard на сервере не блокирует клиентскую
логику синхронно), но **не подтверждено многократным реальным тестом**.
**Что проверить в следующей сессии:** после конверсии worker↔warrior
несколько раз подряд — не сбрасывается ли выделение юнита, не пропадает ли
юнит из горячей группы (Ctrl+1-9), нет ли рассинхрона goal/target между
клиентом и сервером сразу после конверсии. Если что-то из этого сломано —
искать здесь в первую очередь, возможно придётся частично вернуть
отложенный путь только для клиентской синхронизации, оставив немедленный
`discard()` только на сервере.

### Базовое состояние MVP-пайплайна Formix (без изменений с 19–21.07.2026)
- Фракция Formix выбираема в лобби матча и в debug-кнопках быстрого старта.
- `FormixWorkerUnit` — собирает ресурсы (включая item-дропы с животных),
  строит/чинит здания, конвертируется в `FormixWarriorUnit` через ability
  "Call to Arms" у главного здания.
- `FormixWarriorUnit` — боевой (melee), конвертируется обратно через
  "Back to Work"; отвалится сам, если уйдёт дальше 60 блоков от Hive.
- `FormixHive` — главное здание, производит `FormixWorkerUnit`. Иконка —
  honeycomb block (временная).
- Счётчик ресурсов виден только на экране инвентаря, формат "текущее/1000".
- Реальный лимит хранения ресурсов = 1000 на тип, sandbox-игроки исключены.
- RTS-режим (orthoview) разрешён в Survival и Adventure, не только Creative
  — риск не проверен, см. раздел рисков выше.
- Иконки worker/warrior — программные инсектоид-заглушки, не финальный арт.
